Guide

Known target URLs

Every target this dashboard knows an address for. The one marked reachable now is the one that works from where this dashboard is running; the other address for the same service only works the other way (see each note).

The 8 vulnerability templates

Every collection is one of these shapes. All ask the same thing — can one user reach a resource that isn't theirs? — through a different kind of operation, because a fix that only covers the obvious case (a plain GET by id) often still misses the other seven.

B1–B7 map to OWASP API1:2023 Broken Object Level Authorization; V1 maps to API5:2023 Broken Function Level Authorization (a role, not whose data it is). The "defended" build of each runs the matching correct check.

Reading the Findings panel

Exploitable now
The attack succeeded this assessment — one user reached another's resource. The evidence is the actual response that came back.
Corrected
A collection that was exploitable and is now blocked by a verified defender patch. Each shows before (the original exploit) beside after (the verified-secure response), with the remediation that closed it.
Inconclusive
The check could not run cleanly (see its evidence). Never read this as "safe" — it means "unknown".
Secure (never flagged)
Collections that were never exploitable. Counted in the summary but kept out of the list so real issues aren't buried.

How "LLM-sampled checks" works

A Custom API assessment checks every collection instantly with plain HTTP requests — no model, no cost. That is the always-on baseline.

Setting LLM-sampled checks above 0 adds a second opinion: that many random collections are also attacked by your local Ollama model through the same tool-calling setup VAmPI uses — the model decides the request and reads the real response; it is graded from the transcript, never the model's say-so.

Sampled, not exhaustive: the lab keeps growing, so an LLM mission against every collection would take hours to re-prove the same 8 shapes. 5–20 is enough to confirm the baseline and the model agree. Results appear in Findings tagged llm, beside the deterministic finding for the same collection.

Custom API lab growth controls

Growth interval (s)
How often, in seconds, the lab adds one new scenario. Smaller grows faster; 0 freezes growth.
Max collections
A ceiling on total scenarios. Growth pauses at this many; 0 means no ceiling. Raising it later resumes growth live, no restart.
Vulnerability probability
0–1: the odds each new scenario is left vulnerable rather than already secure. Only affects future scenarios.
Templates
Which of the 8 shapes new scenarios may use. Unchecking one only stops it being chosen going forward.
Paused
Stops growth immediately without losing your other settings.

Why an assessment can be slow

A VAmPI assessment (or any LLM-sampled check) loads a local model via Ollama and drives it through several multi-turn tool-calling missions. On a RAM-constrained machine this is genuinely slow — measured on an 8GB machine:

Deterministic only (no LLM)
Sub-2-second regardless of lab size — plain HTTP requests, no model.
Full VAmPI assessment, lab stopped
~218s. The floor: loading a 4.6GB model and running 5 missions sequentially takes minutes on modest hardware.
Full VAmPI assessment, lab running with ~2,000 collections
~315s — about 45% slower. The lab's route table and larger state payload compete with Ollama for RAM.

What helps, in order: pause or reset the lab before an LLM run; use a smaller/quantized model; close heavy unrelated apps; reboot after days of uptime.
