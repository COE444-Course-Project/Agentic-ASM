Known target URLs

Every target this dashboard knows a working address for. The one marked reachable is the one that will actually work if you pick it right now — the other address for the same service only works if this dashboard is run a different way (see note).

What the custom API lab's growth controls mean

Growth interval (s)
The lab's "heartbeat": how often, in seconds, it automatically adds one new vulnerability scenario ("collection") to its API. A smaller number grows the attack surface faster. 0 freezes growth entirely — nothing new appears until you raise it again.
Max collections (0 = unlimited)
A ceiling on the total number of scenarios the lab will ever create. Growth pauses automatically once this many exist. 0 means no ceiling — it grows forever. Raising the cap later resumes growth past the old limit, live, with no restart.
Vulnerability probability
The odds, from 0 (0%) to 1 (100%), that each new scenario going forward is actually left vulnerable rather than already secure. 0.5 is a coin flip (the default) — 0 creates only secure "negative control" cases, 1 makes every new one vulnerable. This never changes scenarios already created, only future ones.
Templates
Which of the 8 known vulnerability shapes (B1–B7, V1 — explained just below) the lab is allowed to pick from for new scenarios. Unchecking one just stops it being chosen going forward; it doesn't remove or change existing collections built from it.
Paused
Stops growth immediately regardless of the interval, without losing your other settings — flip it back off to resume exactly where it left off.

The 8 vulnerability templates

Every collection is assigned exactly one of these on creation. All 8 are the same underlying question -- "can one user reach a resource that isn't theirs?" -- asked through a different shape of API operation, because a fix that only covers the obvious case (plain GET by id) often still misses the other 7.

B1 — GET /documents/{id}
Reads another user's document directly, just by knowing/guessing its id — no ownership check on reads at all.
B2 — POST /exports
Reads stay protected, but exporting the same document via a JSON body reference ({"document_id": …}) skips the ownership check — the flaw hides in a side door, not the obvious path.
B3 — GET /projects/{project_id}/files/{file_id}
Checks you belong to the project you named, but never checks the file actually belongs to that project — pass your own project id with someone else's file id and it's handed over.
B4 — POST /documents/batch
Only the first id in a batch request gets ownership-checked; a victim's id smuggled in second (or later) comes back unchecked.
B5 — PATCH /documents/{id}
Same trap as B2 but for writes: reads are protected, yet you can overwrite another user's document content.
B6 — POST /documents/{id}/share
You can mint a working public share link for a document you don't own. (The link itself being viewable by anyone is by design — the bug is being allowed to create one for someone else's file.)
B7 — GET /organisations/{org_id}/invoices/{id}
Having the "billing" role at all is treated as sufficient — it never checks you actually belong to that organisation, so you can read another tenant's invoice. A cross-tenant leak.
V1 — POST /admin/users/{id}/disable
An ordinary, non-admin user can disable someone else's account — no role check at all. The one role-based (not ownership-based) template; admin is the positive control that's actually supposed to do this.

B1–B7 all map to OWASP's API1:2023 Broken Object Level Authorization; V1 maps to API5:2023 Broken Function Level Authorization (it's about a role, not whose data it is). The "defended" version of each template runs the matching correct check instead.

Why an assessment can be slow

A VAmPI assessment (or any LLM-sampled check) loads a local model into memory via Ollama and drives it through several multi-turn tool-calling missions. On a RAM-constrained machine this is genuinely slow, and gets slower the more else is running at the same time — measured directly on an 8GB machine:

Deterministic-only (no LLM)
Sub-2-second, regardless of how large the lab is. The deterministic checks (VAmPI's 3 "insecure by design" modules, and every custom-API collection) are plain HTTP requests — no model involved, no meaningful slowdown.
Full VAmPI assessment, lab + dashboard stopped
~218 seconds. This is the floor: even with nothing else competing for memory, loading a 4.6GB local model and running 5 LLM-driven missions sequentially just takes a few minutes on modest hardware.
Full VAmPI assessment, lab running with ~2,000 collections
~315 seconds — about 45% slower than the floor above. The lab's in-memory route table and the dashboard's larger state payload compete with Ollama for the same limited RAM and Docker's fixed VM allocation.
The dominant cost either way
A 4.6GB model plus Docker Desktop's VM (commonly ~3.8GB) already add up to more than 8GB of RAM on their own, before anything else on the machine is counted — so even the "floor" case above involves real memory pressure (swapping to disk), which is the main reason it's measured in minutes, not seconds.

What actually helps, in order of impact: pause or reset the lab before running an LLM-driven assessment (smaller effect, but free and immediate — see the confirmation prompt this page shows you for exactly this); use a smaller/quantized Ollama model; avoid running heavy unrelated apps at the same time; and, if the machine has been up for days, a reboot reclaims memory that's gradually fragmented/swapped out over a long uptime.

How "LLM-sampled checks" works

By default, a Custom API assessment checks every collection, instantly, with plain HTTP requests — no LLM, no reasoning, no cost. That stays the fast, exhaustive, always-on baseline.

Setting LLM-sampled checks above 0 adds an optional second opinion on top: that many randomly chosen collections also get attacked independently by your local Ollama model (Ollama model field), through the exact same tool-calling setup VAmPI's checks use — the model decides what request to send and reads the real response back; it's never just taking the model's word for it.

Why sampled, not exhaustive: the lab is unbounded and keeps growing (yours currently has well over a thousand collections) — running an LLM mission against every single one would take hours to re-prove the same 8 vulnerability shapes over and over. A small sample (5–20 is reasonable) is enough to confirm the deterministic baseline and the model agree, without turning every assessment into an overnight job.

Results show up in Findings as "LLM-driven check: …", tagged kind: llm, alongside (not replacing) the deterministic finding for that same collection — so you can compare the two.

Tour of this page

Target URL
Where an assessment runs against. Pick a known address from the dropdown or type any other HTTP(S) URL.
Assessment type
Auto-detect API reads the target's public OpenAPI schema and figures out whether it's VAmPI or the custom lab. VAmPI attacker / Custom API assessment force one and error out if the target doesn't actually match.
Ollama model
Which local LLM drives VAmPI's reasoning-based checks (SQL injection, mass assignment, enumeration, BOLA) and, if set above 0, the custom API lab's "LLM-sampled checks" too. Disabled when neither applies.
LLM-sampled checks
Custom API lab only. 0 (default) keeps the assessment fully deterministic. Above 0, that many randomly chosen collections also get an independent LLM-driven cross-check — see "How LLM-sampled checks works" above. The assessment chip reads "done" the moment the fast deterministic pass finishes, before those LLM calls start; its own "LLM-sampled checks running (N)…" line (and then a result once they finish) is how you tell they're genuinely in progress, not skipped.
Run assessment
Starts one assessment against the Target URL in the background. VAmPI assessments reset its demo database first; custom API ones do not.
Stop
Requests the running assessment to stop. It's cooperative, not instant: whatever single check or collection is already in flight finishes first, then the assessment ends and is recorded as "stopped" with whatever it found so far.
Reset state
Clears this dashboard's saved assessments, findings and log history. It does not touch the targets themselves or the custom lab's growth.
Assessments strip
One chip per past assessment, with its vulnerable/defended/inconclusive counts. "Defended" means currently not exploitable; when any of those were made secure by a verified defender patch (rather than simply never having been vulnerable), the chip breaks that count out as "(N patched, M always secure)".
Attack Surface panel
Every endpoint discovered on the target so far, from its OpenAPI schema.
Findings panel
One row per check that is or was a finding: VULNERABLE means the attack succeeded, defended here means a verified defender patch is blocking a previously-successful attack, and inconclusive means the check itself failed to run cleanly (see its evidence) — never treat inconclusive as "safe". A collection that was simply always secure and never flagged is left out of this list entirely (it isn't a finding); its "defended" count still appears in the assessment chip above.
Live log
A running narration of what the orchestrator/operator/scout are doing, in order, as an assessment executes.
Custom API lab controls
Only shown when the Target URL is the custom lab. Lets you read and change its growth knobs live, from this page, with no shell access needed.
Reset lab
Clears every collection and reseeds to the lab's initial count — the live equivalent of deleting the scenario Docker volume and restarting, without touching Docker at all. Irreversible; asks for confirmation first. Growth settings are kept; the applied remediation policy is not cleared (see the confirmation dialog for why that matters).
